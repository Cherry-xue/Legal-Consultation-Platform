## 二、评价方式

按交付效率、可维护性、协作可观测性、检索扩展、运行成本和部署负担比较。以下“低/中/高”及推荐次序是针对本项目的工程判断，不是第三方排名或已完成的基准测试。

所有候选必须满足：独立业务配置、真实 RAG、原文追溯、用户权限、持久化任务、失败重试与协作调用上限。轻量方案也不能省掉这些基础要求。

## 三、三套候选方案

三套均使用 MySQL、云端模型 API、前后端分离，并保留现有需求与验收范围。方案可按模块混搭，不必整体绑定。

| 模块 | A：轻量实现 | B：平衡实现（建议优先） | C：检索扩展优先 |
|---|---|---|---|
| 前端 | Vue 3 + JavaScript + Element Plus | 同 A | 同 A |
| 后端 | FastAPI + SQLAlchemy | 同 A | 同 A |
| 业务数据 | MySQL | MySQL | MySQL |
| 向量检索 | Chroma 服务模式 | Chroma 服务模式 | Qdrant |
| 五个业务 Agent | Profile + 共用 Runner | Profile + 共用 Runner | Profile + 共用 Runner |
| 协作 Agent | Python 显式状态与并发调用 | LangGraph 显式状态图 | LangGraph 显式状态图 |
| 文档解析 | pdfplumber + python-docx + TXT | 同 A | 同 A，复杂解析再单独升级 |
| 索引任务 | MySQL 任务表 + 独立 worker | 同 A | 同 A |
| 检索起点 | 向量 Top-K + 元数据过滤 | 向量 Top-K + 元数据过滤 | 向量检索，按需求增加混合检索 |
| 部署 | Compose | Compose | Compose |
| 相对新增学习负担 | 低，但需自己写编排设施 | 中，集中于 LangGraph | 中至较高，另需掌握 Qdrant |

### 3.1 A：轻量实现

适合：工期很紧、协作始终限定为两个业务 Agent 的一次分工，团队更熟悉普通 Python 服务。

优势是依赖少、控制流直观。基础 Agent 直接检索和生成，协作通过计划、并发执行、汇总三个服务完成。

代价是运行状态、事件、重试、恢复等行为需要自行设计和维护。能保存业务任务状态不代表自动获得图节点级恢复；若以后增加条件分支与多轮流程，手写编排成本会增长。

选择条件：更看重尽快交付，接受协作编排由项目自行维护，不以框架名称作为加分点。

### 3.2 B：平衡实现（建议优先）

适合：当前“开发效率与工程完整度平衡”的目标，且初期资料规模与并发不大到需要专门优化。

基础五个 Agent 维持清晰的 Runner，协作 Agent 单独使用 LangGraph 表达计划、两个子任务、冲突检查和汇总。Chroma 先满足向量检索、元数据过滤和独立服务部署，保留检索适配层。

优势是延续原规划候选，减少切换成本，同时能清晰展示真实协作状态。LangGraph 的框架能力不自动等于业务日志、界面进度和重启恢复，这些仍需接入及验证。[官方框架说明](https://www.langchain.com/oss-overview)、[Chroma 客户端/服务端模式](https://docs.trychroma.com/production/chroma-server/client-server-mode)

代价是同时维护 MySQL 与向量索引，需要任务及对账机制；复杂混合检索如采用应用层融合，会增加代码。

推荐理由是减少本阶段组件和设计变化，不是认定 Chroma 性能优于 Qdrant。

### 3.3 C：检索扩展优先

适合：希望较早将多路检索、多阶段查询、较复杂过滤作为项目重点，愿意投入向量服务配置与调试。

MySQL 继续保存业务主数据，Qdrant 保存向量和检索载荷，协作编排与 B 相同。Qdrant 的 Query API 支持混合与多阶段查询；这些能力仍需要选择合适的向量、索引与排序配置，不能仅更换数据库就自动提升中文法律召回。[官方混合查询说明](https://qdrant.tech/documentation/search/hybrid-queries/)

代价是新增服务学习与适配成本。相对 B 仍然是双存储结构，并没有消除同步问题，也不能凭服务名称保证更低延迟或更高召回。

选择条件：明确希望第一阶段就做检索策略扩展，并接受相应调试投入。若近期只做基础向量问答，它的部分能力可能暂时用不到。

## 四、关键模块逐项比较

### 4.1 前端：Vue 3 与 React

前端语言采用 JavaScript。Vue 单文件组件使用 `<script setup>`，脚本模块使用 `.js`，Vite 配置使用 `vite.config.js`；不要求 TypeScript 编译或类型检查。接口数据校验、必要的 JSDoc 和 ESLint 在实现时按需配置。后端仍采用 Python + FastAPI。

| 方向 | Vue 3 + Element Plus | React + Ant Design |
|---|---|---|
| 本项目匹配 | 延续原规划，适合菜单、表格、表单及管理页 | 也能覆盖同类页面 |
| 主要取舍 | 若已熟悉 Vue，切换成本低 | 若已熟悉 React，优先复用经验 |
| 本轮建议 | 暂建议保留 | 有明确熟悉度优势时替换 |

前端选择主要由团队经验决定，不声称任一框架天然更适合 AI。框架及 UI 组件的具体版本、许可证和依赖兼容性在确定候选后核验。

### 4.2 后端：FastAPI 与 Django

FastAPI 与原规划的异步模型调用、SSE 和独立服务结构一致，建议保留。Django 在已有 Django 经验、后台管理需求更重时值得考虑，但没有必要仅为本项目增加一次框架迁移。这里是项目匹配判断，不是框架性能排名。

### 4.3 向量存储：Chroma 与 Qdrant

| 维度 | Chroma | Qdrant |
|---|---|---|
| 基础向量检索 | 覆盖候选所需基本能力 | 覆盖候选所需基本能力 |
| 部署 | 可独立 Docker 服务与 HTTP 客户端 | 可 Docker 部署 |
| 本项目初始接入 | 延续原规划候选，适配变化较少 | 需要替换对应客户端和查询模型 |
| 检索扩展 | 按选定功能验证，必要时应用层融合 | 官方提供混合及多阶段查询 API |
| 共同要求 | 权限过滤、版本关联、删除同步、持久化与备份 | 同左 |

能力依据：[Chroma Docker](https://docs.trychroma.com/deployment/docker)、[Qdrant 安装](https://qdrant.tech/documentation/installation/)、[Qdrant 查询](https://qdrant.tech/documentation/search/hybrid-queries/)。不在尚无样本与压测时给出容量分界或性能分数。

建议使用 VectorStore 接口隔离 upsert、search、delete 与健康检查；统一结果保留 chunk_id、分数类型、元数据和来源版本。适配层可降低切换成本，但不能做到无成本迁移，换库仍需重建和回归。

### 4.4 协作：显式调用与 LangGraph

| 维度 | Python 显式调用 | LangGraph |
|---|---|---|
| 两个固定子任务 | 可以实现 | 可以实现 |
| 控制流 | 服务代码与自定义状态 | 节点、边与结构化状态 |
| 扩展条件分支 | 自行组织 | 可显式建模 |
| 检查点与恢复 | 自行实现 | 框架提供相关机制，需配置持久化与正确运行标识 |
| 本项目建议 | 候选 A | 候选 B/C |

不把“用了 LangGraph”视为协作完成。验收仍检查两个真实业务 Agent、各自 RAG、引用追溯与失败处理。[官方说明](https://www.langchain.com/oss-overview)

### 4.5 索引任务：独立 worker 与 Celery

初期建议 MySQL 持久化任务表 + 独立 worker，不默认增加 Redis。任务必须有原子领取、租约、重试次数、超时回收、幂等写入及失败可见性，不能只写循环查询就宣称可靠。

Celery 作为需要多 worker 扩展或复杂调度时的候选，实际 broker、重试与任务幂等仍需配置。FastAPI BackgroundTasks 适合响应后的轻量工作，不作为需要重启恢复的索引任务队列；官方也提示重型后台工作可以考虑 Celery 等工具。[FastAPI 官方说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

### 4.6 文档解析

首期建议 pdfplumber、python-docx、TXT 加自定义条文结构识别，控制支持范围并人工预览。复杂 PDF、扫描件、表格比例高时再评估 Docling 等解析流水线，不能假设普通 PDF 抽文本自然等于可靠法律层级识别。

Docling 提供 OCR 与表格处理配置，但应在实际中文法律资料上验证依赖、吞吐、定位和精度，再决定是否引入。[官方配置说明](https://docling-project.github.io/docling/usage/advanced_options/)

## 五、模型服务选型：第二轮单独决定


| 能力 | 候选方向 | 决策方法 |
|---|---|---|
| 生成及协作计划 | 中文通用指令模型 API；以结构化输出及证据约束为重点 | 两个候选、同题对照；检查 JSON、条件化说明、引用与延迟 |
| Embedding | 云端中文/多语言向量 API；本地作为另行选择 | 用法律术语、口语、长条文测 Recall@5；记录维度和模型版本 |
| Rerank | 首期不加；召回充分但排序差时再考虑云端重排 | 同一候选集比较前五条命中与额外耗时 |


成本按“索引嵌入 + 查询嵌入 + 各节点生成输入输出 + 可选重排”分别记录。协作的两次业务生成、计划和汇总都计费；缓存及重试单独计数。预算、可接入区域及网络条件确定后，再查官方定价并估算日/月成本。

### 8.3 配置优先级与兼容策略

- 优先级为进程环境变量 > 本项目 `.env` > 显式指定的共享凭据文件 > 默认值。多文件加载时共享在前、本项目在后，路径从项目根计算，不依赖运行目录。
- 开发阶段只从共享文件读取必要的百炼凭据，禁止继承智能家居的数据库地址、库名或其他服务设置。部署时通过环境注入凭据，不依赖机器上的上级目录结构。
- Agent 与模型使用显式键值绑定，不按列表顺序取模。日志记录 Agent、模型 ID、请求 ID、耗时和用量，不记录密钥或完整敏感输入。
- 思考开关、结构化输出、工具调用、temperature 等参数按模型能力配置。参考项目的 `enable_thinking=false` 是兼容线索，不对所有型号盲目发送相同参数。[百炼兼容接口说明](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)
- LangChain Embedding 客户端采用原始字符串输入，参考 `check_embedding_ctx_length=false`；批量条数及长度按选定模型验证，不把参考项目的 10 条当作所有模型统一上限。




## 九、客户账号与头像选型

- 账号密码认证，scrypt 哈希；数据库保存哈希后的服务端会话，客户端通过 HttpOnly Cookie 使用会话，不采用手工凭据输入。
- MySQL 保存用户、会话与记忆，复用现有数据库，不增加 Redis。登录限流暂为单进程内存实现，多实例部署需另行统一限流状态。
- Vue 原生 Canvas 实现头像拖动和缩放裁剪，避免为单一功能增加 UI 依赖；Pillow 在后端执行校验与重编码。
- 客户端只呈现注册、登录、个人中心、咨询和个人资料操作；维护入口通过后端角色或终端命令执行。
