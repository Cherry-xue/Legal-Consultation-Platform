## 客户账号实施补充（优先于旧的会话约定）

已新增 users、user_sessions、conversations、chat_messages、user_memories。现有 documents 和 agent_runs 的 owner 保存真实用户 ID；旧开发记录保留原归属，不自动分配给新用户。

客户端新增 /login、/register；新增 /api/auth/register、login、logout、me、password、avatar，以及 /api/conversations、/api/memories 相关接口。用户可恢复历史会话并继续追问，替代旧的单轮会话边界。

数据库迁移通过 scripts/migrate.py 执行；移除客户端初始化接口。服务检查只限后台管理员。客户界面隐藏模型名、运行编号、基础设施状态和内部错误码。资料菜单面向个人材料，不允许普通用户发布公共法律知识。

## 二、架构与技术栈

```text
Vue 3（基础 8 菜单 / 含协作 9 菜单 / 含调试 10 菜单）
    │ HTTP + SSE
FastAPI：身份、权限、参数校验、限流、任务与错误反馈
    ├─ 五个业务 Agent → 共享 AgentRunner → RAG
    ├─ 协作 Agent（附加题）
    │    → 两个受控子任务 → 各业务 Agent 独立 RAG → 汇总与引用校验
    ├─ RAG：上传 → 解析 → 预览切块 → 确认 → 嵌入 → 索引 → 检索
    ├─ MySQL：来源、版本、块、任务、会话、引用与执行记录
    └─ Chroma：可重建的向量索引
```

| 部分 | 方案 | 说明 |
|---|---|---|
| 后端 | Python 3.11、FastAPI、Pydantic、SQLAlchemy async | API、业务及数据模型 |
| 编排 | 基础显式服务调用；协作使用 LangGraph 状态图 | 单轮问答无需额外循环 |
| 前端 | Vue 3、JavaScript、Vite、Pinia、Element Plus | 菜单、会话、任务与引用 |
| 解析 | pdfplumber、python-docx、TXT 解析 | 先检测扫描件，OCR 可选 |
| 存储 | MySQL、Chroma 服务模式 | 主数据与派生索引分离 |
| 任务 | MySQL 持久化任务表 + 独立 worker | 原子领取、租约、超时回收、幂等与重试 |
| 模型 | 百炼云端 API；各 Agent 独立生成模型配置、统一 Embedding | 候选见选型文档第八节，密钥仅后端保存 |
| 部署 | Docker Compose、Nginx | 锁版本、健康检查、SSE 禁止缓冲 |

实现时核验并锁定依赖及镜像版本，不以 latest 作为可复现基线。更换 Embedding 模型或维度时新建索引版本，不混用旧向量。

前端采用 JavaScript：Vue 组件使用 `<script setup>`，模块使用 `.js`，Vite 配置使用 `vite.config.js`。构建流程不依赖 TypeScript 类型检查；接口入参和响应的必要校验由运行时代码处理。后端保持 Python + FastAPI。

## 三、五个业务 Agent

| code | 菜单 | 职责 | 输出 |
|---|---|---|---|
| contract | 合同审查 | 商事条款理解及风险 | 条款、风险、依据、修改方向、待确认项 |
| labor | 劳动争议 | 工资、加班、解除、补偿及劳动程序 | 主张项目、条件、时效与材料 |
| family | 婚姻家事 | 财产、抚养、继承 | 关系说明、规则、待补事实 |
| consumer | 消费维权 | 退换货、质量与平台责任 | 救济路径、依据与证据 |
| procedure | 诉讼程序 | 管辖、起诉、举证、期限与执行 | 步骤、材料、期限计算前提 |

每个 Profile 包括 code、职责、system_prompt、允许知识范围、输出模型和业务示例。共用 Runner 不影响独立定位，以实际输出及检索记录验证差异，不只检查名称不同。


基础采用共享法律资料与业务域关联表，后端根据 Profile 计算检索范围。相关实体与程序知识允许重叠。用户请求不能覆盖授权范围；一域一 collection 是可选组织方式，不是权限机制。精确检索、向量检索、原文接口均校验用户及资料权限。

不相关问题说明职责并建议切换；相关问题可在主责范围内回答，不追求跨域拒答率 100%。会话创建时固定 Agent，切菜单加载或新建对应会话，不把上一 Agent 上下文带入另一业务。

## 四、协作咨询 Agent（附加题）

### 4.1 定位与入口

第六个 Agent，code 为 collaboration，路由 `/agent/collaboration`。针对同一事项的两个业务领域分工、执行并汇总，复用已有业务 Agent，不另建万能知识库。

示例：消费纠纷中的责任和退款问题交给 consumer；管辖与起诉材料交给 procedure。双域问题必须实际调用两个不同业务 Agent，且各自调用 RAG。单领域问题可以建议切换，不伪造第二个任务。

### 4.2 状态图

```text
输入校验 → 提取已有事实 → 计划两个子任务 → 白名单与预算校验
                                          │
                         ┌────────────────┴────────────────┐
                         ▼                                 ▼
                   业务 Agent A                       业务 Agent B
                   自有范围 RAG                       自有范围 RAG
                         └────────────────┬────────────────┘
                                          ▼
                               收集结果（允许部分失败）
                                          ▼
                              前提及冲突检查 → 汇总草稿
                                          ▼
                                引用校验 → 发布结果
```

服务端只允许调用五个业务 Agent，不允许递归调用协作 Agent 或任意外部工具。一轮协作、最多两个子任务和两个不同 Agent。基础子任务单轮检索；若选做 Agentic，每个子任务最多两轮总检索。

初始预算：总超时 30 秒、单子任务 15 秒、汇总最多 12 个去重证据块，均为待压测的配置初值。设置上下文 token 上限，优先保留直接支持结论的证据；不能截断后伪称完整条文。

并发执行分别捕获子任务错误与超时，成功结果继续保留。用户取消向两个子任务、检索和模型请求传播。不得因一个异常而丢弃另一个已完成结果。

### 4.3 结构化契约

```text
CollaborationTask
  task_id, agent_code, question, known_facts, missing_facts, deadline

AgentResult
  task_id, agent_code, status(completed/no_basis/failed/cancelled)
  claims[{text, assumptions[], evidence_ids[]}]
  missing_facts[], warnings[], retrieval_log_ids[], error_code?

CollaborationResult
  run_id, status(completed/partial/failed/cancelled)
  tasks[], summary, conflicts[], missing_facts[], citations[]
```

证据 ID 指向后端保存的文档版本与块，不由模型自由生成。检查子 Agent 返回的 ID 是否属于该任务的授权命中。汇总只用校验后的结论及原证据，不能仅把子 Agent 的文字当法律依据。

统一引用以 `(document_version_id, chunk_id)` 去重并重新编号，保留子任务来源。最终每个需证据结论关联支持它的引用；不能将全部召回资料都列为“已引用”。

### 4.4 冲突与失败降级

先检查结论差异是否源于时间、地区或事实前提。可解释时分条件展示；无法解释时列分歧、来源与待补事实，标记人工复核，不强行统一。

单任务失败显示 partial，明确成功领域与缺失领域；两个任务都失败或无充分依据时不生成综合法律结论。重试创建新运行记录，不覆盖失败历史。前端显示用户可理解的任务摘要与状态，不展示内部推理或未校验的中间输出。

## 五、RAG 实现闭环

### 5.1 上传、预览与向量化

上传保存原文、来源和版本，创建解析任务。状态包含 `uploaded → parsing → parsed → indexing → indexed`，失败保存 failed_stage、错误码及可重试条件。

预览为独立草稿，包含 preview_id、文档版本、参数摘要、解析器版本及有效期。确认有效预览后创建索引任务；重复确认通过幂等键返回原任务，避免重复入库。

嵌入按批执行，向量使用稳定 chunk ID。校验索引数量、内容哈希及版本后才标记可用；未完成索引不参与正式问答。页面能查询任务状态与失败原因，不能在后台失败后仍显示成功。

限制文件类型、大小、解析时间、块数。损坏文件、空文本及扫描件需 OCR 时明确反馈；OCR 初期可不支持。

### 5.2 切块及原文定位

- 法律资料优先按条识别，保留编、章、节、条、款、项；普通资料按段落兜底。
- 款按真实段落结构确认，“（一）（二）”通常是项，不能直接编号成款。
- 超长条文保留父条关联，细分记录续块序号，不编造款号。
- 检索前缀与原文分开存，不把首行正文当标题重复拼接。
- 保留字符偏移、PDF 页码及上下文，原文展示基于同一文档版本。
- 示例法条必须从官方原文核验，不硬编码不真实的款数；虚构测试条文明确标注。

### 5.3 检索与回答校验

基础实现真实向量 Top-K 检索，展示分数及其类型、来源、版本和命中片段。BM25、RRF、精确条号和术语映射为可选增强，不能代替向量检索。

精确检索以法名、版本及条号定位；法名不明时澄清或列候选。术语映射允许同词关联多条依据，匹配区间按实际命中别名长度计算，不因去重丢失同词其他条文。

问答流程：检索 → 版本与适用条件检查 → 草稿 → 引用及支持关系检查 → 发布。检查来源 ID、原文条号、引用与结论支持关系；语义支持检查结合人工抽检，不宣称绝对可靠。

失败最多受控修复一次，仍失败则删除无支持结论或返回 NO_BASIS。无证据或事实不足时不强制输出完整五段。

基础 SSE 先发送进度事件，校验通过后再发送正文分片；不能把分类、分解、充分性判断等所有模型输出直接作为正文 delta。首状态与首个校验后正文分别计时。

### 5.4 可选 Agentic 检索

```text
识别及拆争点 → 检索第 1 轮 → 充分性判断
                                ├─ 不足 → 改写 → 检索第 2 轮
                                └─ 充分 ────────────┐
                                                   ▼
                          版本与适用检查 → 草稿 → 校验 → 发布
```

两轮是首轮加一次重试；耗尽后证据不足走 NO_BASIS 或仅回答有依据部分，不无条件继续生成确定结论。每轮记录问题、争点、命中、策略与耗时。框架本身不作为能力证明。

## 六、法律知识与数据模型

### 6.1 来源与版本

先为每域准备少量核验过的官方资料和可靠演示问题，再扩展覆盖范围。记录资料名称、版本、官方链接、获取日期、覆盖条文、施行及失效时间、核验人与时间。按所选场景复核需求文档列出的相关新解释，演示前再次确认。

法律实体与具体版本分开。效力状态采用 pending_effective/current/repealed/unknown；修订产生新版本，不用含混的 amended 状态代替适用判断。

效力标签与案件适用版本分开展示。历史事实可能适用历史规定，不能看到废止就机械替换。缺少必要时间、过渡规则或事实时给出条件化说明。

新旧法对应表是可选人工资产，支持一对多、多对一、内容变更和无对应，保存依据与审核信息。旧法原文查询可返回历史条文并标注状态；对应新法只是导航，不自动决定适用。

### 6.2 核心表

| 表 | 关键字段或关系 |
|---|---|
| users、roles | 用户、角色及管理权限 |
| documents | owner_id、visibility、source_url、deleted_at、保留策略 |
| document_versions | document_id、hash、原文位置、版本、解析器版本 |
| laws、law_versions | 法律实体、发布日、有效区间、状态、核验信息 |
| law_articles | law_version_id、条号、原文及定位；版本与条号唯一 |
| article_parts | article_id、parent_id、层级、序号、内容及偏移 |
| knowledge_domains、domain_documents | 业务域与资料关联，允许复用 |
| chunk_previews、chunks | 参数、文档版本、父条文、定位、内容哈希 |
| index_jobs、index_outbox | 索引版本、阶段、幂等键、重试、错误、完成时间 |
| conversations、messages | owner_id、agent_code、状态、正文、耗时 |
| retrieval_logs | message_id、task_id、轮次、范围、命中、策略、耗时 |
| message_citations | message_id、文档版本、chunk_id、支持结论、核验快照 |
| collaboration_runs | 用户、会话、总状态、预算与起止时间 |
| collaboration_tasks | run_id、agent_code、子问题、结构化结果、错误与执行记录 |
| eval_cases/runs/results | 集合版本、模型及语料快照、配置、结果 |

证据外键与来源字段不以模型文字代替。公共法律资料与私人合同分开授权存储；私人合同不自动进入公共知识库。

### 6.3 主数据与向量一致性

MySQL 与 Chroma 不假设共享事务。主事务保存元数据及 outbox 任务，worker 幂等写向量；检查数量、版本和哈希后标记索引可用，支持失败重试、对账和重建。

文档删除用 deleted_at，法条废止用版本效力状态，索引用任务状态。删除先让文档退出查询范围，再异步清理向量及缓存。公共历史资料按保留政策追溯；私人资料按删除规则清除原文与派生数据，历史回答显示来源已删除。不得通过把删除文档标成“法律废止”来处理。

## 七、前端与接口

### 7.1 页面与状态

路由按需求文档菜单表执行。基础八页、附加协作页、可选调试页的数量保持一致。向量化入库在切块页有明确按钮和进度，不另设强制菜单。

回答页展示正文及引用面板；协作页增加分工、子任务状态、差异及待补事实。原文抽屉展示来源、版本、核验时间、片段及上下文，并检查权限。

### 7.2 REST 契约

```text
GET    /api/health
GET    /api/agents
POST   /api/conversations                    # {agent_code}
POST   /api/agents/{code}/chat                # {conversation_id, query, facts?}，SSE

POST   /api/rag/documents                    # 文件及来源元数据
GET    /api/rag/documents
DELETE /api/rag/documents/{id}               # 删除任务或状态
POST   /api/rag/documents/{id}/reindex
GET    /api/rag/jobs/{job_id}
POST   /api/rag/chunks/preview               # 返回 preview_id、摘要及预览
POST   /api/rag/chunks/commit                # {preview_id, idempotency_key} → job_id
POST   /api/rag/retrieve                     # {query, top_k, domain?}，后端授权范围
GET    /api/rag/sources/{chunk_id}           # 原文、上下文、定位及版本

# 附加题：协作 chat 使用统一 Agent 接口，额外产生 task 事件
POST   /api/agents/collaboration/chat
GET    /api/collaboration/runs/{run_id}

# 可选增强
POST   /api/rag/retrieve/compare
POST   /api/contracts/reviews               # 合同、类型、审查立场 → job_id
GET    /api/contracts/reviews/{id}
GET    /api/contracts/reviews/{id}/report
```

协作通过注册表统一分发或明确静态路由，避免与动态 code 路由产生歧义。全文审查与导出未实现时隐藏相关入口，基础合同问答通过 chat 完成。

### 7.3 SSE 与错误

| 事件 | 载荷 | 前端表现 |
|---|---|---|
| stage | request_id、stage、detail | 处理进度 |
| task | run_id、task_id、agent_code、status、summary | 协作分工与子任务状态 |
| delta | message_id、text | 校验后的最终正文分片 |
| citations | message_id、items | 引用及子任务来源 |
| error | code、message、retryable、failed_stage | 原因与恢复入口 |
| done | status、usage、timings、run_id? | completed/partial/failed/cancelled |

建立流前用 HTTP 返回身份或参数错误；流建立后使用 error 与终态 done，不让客户端无限等待。采用 fetch POST 流，初版不支持透明断线续传；重试作为新运行，避免消息重复保存。

错误码至少包括 INVALID_FILE、PARSE_FAILED、PREVIEW_EXPIRED、INDEX_FAILED、KB_EMPTY、NO_BASIS、FACTS_REQUIRED、FORBIDDEN、LLM_TIMEOUT、CHILD_AGENT_FAILED。不相关业务优先给切换建议，不一律以错误拒答。

## 八、目录、部署与运行约束

```text
backend/app/
  routers/             # Agent、文档、块、检索、任务、协作
  agents/              # Runner、五个 Profile、提示词与输出模型
  collaboration/       # graph、planner、executor、aggregator、校验（附加题）
  rag/                 # loader、splitter、embedder、indexer、retriever、verifier
  workers/             # outbox、索引、删除、对账
  db/                  # 模型、迁移、会话
  core/                # 权限、配置、限流、错误、日志
frontend/src/
  views/agents/        # 五个业务页；附加协作页
  views/rag/           # Knowledge、Chunks、Retrieval；可选 Debug
  components/          # SourceViewer、CitationCard、JobStatus、TaskTimeline
evals/                 # 开发集、独立验收集及脚本
docs/                  # 需求与规划；实施时补运行及接口说明
```

Compose 包含 frontend、backend、worker、mysql、chroma，worker 复用后端镜像。用服务名通信，配置持久化卷、迁移与健康检查。MySQL 和 Chroma 默认只在内部网络开放，Nginx 代理 API 并禁用 SSE 缓冲。

数据库使用最小权限账号，密钥从环境或部署密钥配置读取，示例不含真值。数据卷路径按锁定版本验证。备份覆盖主数据、原文件和索引重建配置，验证恢复步骤。

LangGraph 调用与读取检查点使用相同运行标识；内存检查点不宣称具备重启恢复。需要恢复时使用经验证的持久化存储。日志保留运行摘要和错误，不记录密钥和未脱敏私人原文。

## 九、评测与验收

### 9.1 顺序与样本

先执行 BASE-01 至 BASE-06，保存请求 ID、截图、检索记录及原文证据；通过后冻结基础版本，再执行 COL-01 至 COL-05。五个 Agent 各至少一条独立业务问题及真实 RAG 引用，不只验证页面数量。

| 附加用例 | 实施检查点 |
|---|---|
| COL-01 | 两个不同业务 Agent 的调用记录及各自检索记录齐全 |
| COL-02 | 注入单子任务超时，成功结果保留且总状态为 partial |
| COL-03 | 构造前提差异与冲突结果，汇总分别标明条件或待复核分歧 |
| COL-04 | 注入越权 Agent 和递归计划，执行前由服务端拒绝 |
| COL-05 | 检查统一引用编号、去重及子任务到原文的完整关联 |

开发集至少 20 条，独立验收集至少 50 条，协作附加用例另列。验收集不用于提示词或阈值调优，报告保留模型、语料、索引、提示词及参数快照。

### 9.2 指标口径

| 指标 | 定义 | 初始目标 |
|---|---|---|
| 引用准确率 | 来源、版本、条号及原文均对应的引用 / 全部引用 | ≥95% |
| 引用支持率 | 人工标注被证据支持的结论 / 需证据的结论 | ≥90% |
| 域内可回答率 | 有充分依据且成功回答的题 / 有充分依据的域内题 | ≥90% |
| 错误拒答率 | 有充分依据却拒答的题 / 有充分依据的域内题 | ≤10% |
| 无依据处理正确率 | 明确说明且未编造结论的无依据题 / 无依据题 | ≥90% |
| Recall@5 | 各题前五条命中的标准相关条数 / 该题标准相关总数，再按题平均 | ≥85% |
| 效力与适用处理 | 固定版本集上标签、前提及缺失事实处理正确题 / 该类题 | 固定集全通过 |
| 协作执行正确率 | 双 Agent 真实调用且引用可追溯的运行 / 正常双域用例 | COL 固定集全通过 |

目标为初始门槛，结果以实测为准。分母为零的指标记为不适用并报告样本数，不能记成 100%。版本、引用存在、分析正确分开评价，固定集全通过不代表开放场景零错误。

延迟分别统计首个状态事件、首个校验后正文、完整回答的 P50/P95。初始完整回答预算基础 15 秒、协作 30 秒，注明并发、样本数、输出长度、模型、网络及冷热启动；不能用期望值推导 P95。

### 9.3 可选对照

| 对照 | 唯一改变 | 观察 |
|---|---|---|
| A/B | 相同单轮链路，不启用/启用术语或混合检索 | 召回与引用 |
| B/C | 相同检索配置，单轮/最多两轮 Agentic | 争点覆盖、正确率、延迟与成本 |
| D/E | 相同双域问题，单业务/协作 Agent | 双域覆盖、引用支持、失败处理与成本 |

比较使用相同输入资料权限与模型，明确变化因素和限制，不把单一开关的增益归因于整个 Agentic。效力及安全检查默认开启；消融只在独立评测环境执行，标明不可用于正式咨询。

### 10.2 风险清单

| 风险 | 措施 |
|---|---|
| Agent 仅名称不同 | 职责、输出结构、样例与调用记录共同验收 |

## 十一、演示与开工顺序

基础演示：五个业务菜单各问已核验问题并展开引用；上传新测试文档、调整切块、确认向量化、查询状态、检索原文；展示一次失败反馈与真实菜单切换。

附加演示：消费与诉讼程序综合问题，展示两个子任务、实际检索、统一引用和汇总；再模拟一个子任务失败，验证部分完成。缓存回放作为备用时明确标记，不伪称实时调用。

开工顺序：冻结 BASE/COL 用例和样例 → 定接口及版本模型 → 一份文档完整 RAG → 五个业务 Agent → 基础前端与验收 → 协作 Agent。后续持续维护需求到实现及验收证据的对应表。
